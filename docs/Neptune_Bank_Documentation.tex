\chapter{Introduction}

\section{Project Overview}
Neptune Bank is a secure online banking system built using a microservices architecture with Spring Boot 3.5.5 and Java 21. The system provides comprehensive banking functionality including user registration with KYC verification, account management, real-time fund transfers, transaction history tracking, and OTP-based multi-channel authentication.

The system is designed with security as a first-class concern, employing RSA-based JWT authentication, BCrypt password hashing, and role-based access control across all services.

\section{Key Features}
\begin{itemize}[leftmargin=*]
    \item \textbf{User Management}: Complete user registration with KYC document upload (Aadhaar, PAN, photo, signature), profile management with CRUD operations, and soft-delete capability.
    \item \textbf{Account Management}: Multi-type account creation (Savings, Current, Fixed Deposit), branch-based account association, balance management with optimistic locking.
    \item \textbf{Fund Transfers}: Secure inter-account fund transfers with RabbitMQ-based asynchronous debit/credit operations, automatic rollback on failure, and comprehensive transaction tracking.
    \item \textbf{Transaction History}: Complete transaction audit trail with filtering by account, chronological ordering, and detailed transaction metadata.
    \item \textbf{OTP Authentication}: Multi-channel OTP delivery via SMS (TextBee API) and Email (SMTP), with expiry management and verification tracking.
    \item \textbf{Security}: RSA-256 JWT tokens, BCrypt password hashing, role-based authorization (ADMIN, USER, EMPLOYEE), and Spring Security filter chains.
\end{itemize}

\section{Security Architecture}

\subsection{Authentication Flow}
\begin{enumerate}
    \item Client sends credentials to \texttt{POST /auth/login} on auth-service.
    \item Auth-service validates credentials using BCrypt comparison.
    \item On success, auth-service generates an RS256 JWT token signed with the private key.
    \item Client includes the JWT in the \texttt{Authorization: Bearer <token>} header for subsequent requests.
    \item Each service validates the token using the corresponding RSA public key.
\end{enumerate}

\subsection{JWT Token Structure}
\begin{lstlisting}[style=jsonstyle, caption={JWT Claims}]
{
    "sub": "username",
    "role": "ADMIN | USER | EMPLOYEE",
    "iat": 1718150400,
    "exp": 1718161200
}
\end{lstlisting}

The token is signed with RS256 (RSA + SHA-256) using a private key (\texttt{private.pem}) and validated with the corresponding public key (\texttt{public.pem}). Token expiry is set to 3 hours.

\subsection{Password Security}
All user passwords are hashed using \texttt{BCryptPasswordEncoder} before storage. The BCrypt algorithm uses a cost factor of 10 (default), generating unique salts for each password. Plaintext passwords are never stored or logged.

\subsection{RabbitMQ Listeners}
The account-service exposes three RabbitMQ listeners for inter-service operations:

\begin{enumerate}
    \item \textbf{Account Validation Listener} (\texttt{account-validation-queue}): Receives an account number string, returns \texttt{true} if the account exists.
    \item \textbf{Debit Listener} (\texttt{account-debit-queue}): Receives \texttt{\{accountNumber, amount\}}, debits the balance atomically. Returns \texttt{false} if insufficient funds.
    \item \textbf{Credit Listener} (\texttt{account-credit-queue}): Receives \texttt{\{accountNumber, amount\}}, credits the balance atomically.
\end{enumerate}

\subsection{Update Authorization}
Account updates are subject to role-based restrictions:
\begin{itemize}
    \item \textbf{Account Owner}: Can only change the mode of operation.
    \item \textbf{Admin}: Can change account type, branch, balance, and ownership (userId).
\end{itemize}

\subsection{Fund Transfer Flow}
The fund transfer process follows a saga-like pattern with compensating transactions:

\begin{enumerate}
    \item \textbf{Validation}: Verify source and destination accounts are different and both exist (via RabbitMQ to account-service).
    \item \textbf{Record}: Save a new transaction record with status \texttt{PENDING}.
    \item \textbf{Debit}: Send debit request to account-service via \texttt{account-debit-queue}.
    \item \textbf{Credit}: On successful debit, send credit request via \texttt{account-credit-queue}.
    \item \textbf{Rollback}: If credit fails, automatically reverse the debit by crediting the source account back.
    \item \textbf{Finalize}: Update transaction status to \texttt{SUCCESSFUL} or appropriate failure status.
\end{enumerate}

\begin{warnbox}[Failure Handling]
If the debit succeeds but the credit fails, the system automatically reverses the debit by crediting the amount back to the source account, and the transaction is marked as \texttt{FAILED\_TECHNICAL\_ERROR}.
\end{warnbox}

\subsection{Transaction History}
The \texttt{GET /transactions/account/\{accountId\}} endpoint returns all transactions where the given account is either the source or destination, ordered by transaction date descending (most recent first).

\section{Message Serialization}
All services use \texttt{Jackson2JsonMessageConverter} for JSON-based message serialization/deserialization over RabbitMQ, ensuring type-safe communication between producers and consumers.

\section{RPC Pattern}
The system uses RabbitMQ's request/reply pattern (\texttt{convertSendAndReceive}) with a 5-second reply timeout. This provides synchronous-like behavior over asynchronous messaging for operations that require immediate confirmation (e.g., account validation before proceeding with a transfer).

\section{Run Order}
Services should be started in the following order to satisfy dependencies:

\begin{enumerate}
    \item \textbf{auth-service} (port 8086) -- no dependencies
    \item \textbf{otp-service} (port 8082) -- no inter-service dependencies
    \item \textbf{user-service} (port 8080) -- RabbitMQ listener (consumed by account-service)
    \item \textbf{account-service} (port 8083) -- depends on user-service via RabbitMQ
    \item \textbf{transaction-service} (port 8084) -- depends on account-service via RabbitMQ
\end{enumerate}

\chapter{Conclusion}
The Neptune Bank Online Banking System provides a comprehensive, secure, and scalable banking platform built on modern microservices principles. The system successfully implements:

\begin{itemize}[leftmargin=*]
    \item \textbf{Security}: RSA-based JWT authentication with BCrypt password hashing
    \item \textbf{Account Management}: Full lifecycle management with branch associations and role-based access control
    \item \textbf{Fund Transfers}: Reliable inter-account transfers with saga-pattern compensation
    \item \textbf{Transaction History}: Complete audit trail with chronological tracking
    \item \textbf{User Management}: Comprehensive user profiles with KYC document management
    \item \textbf{OTP Verification}: Multi-channel (SMS + Email) one-time password system
\end{itemize}

The microservices architecture ensures independent scalability, fault isolation, and technology flexibility for each service component. The use of RabbitMQ for inter-service communication provides reliable asynchronous messaging with request/reply patterns for synchronous-like operations.
